# Add "Event Recording + Replay Regression" to Gradio Apps

## The Problem We Ran Into

We built a dozen or so internal tools with Gradio, each handed to a different colleague to maintain. Whenever a shared backend function gets changed, or some component's usage gets upgraded, several pages quietly "change behavior", and we often only find out when real users complain. We've been burned a few times:

- An ingested CSV-cleaning function was "optimized" once, and one report page's output gained an extra column — users thought the data was dirty;
- Someone changed a shared inference function from raising `ValueError` to returning an empty list, and a caller on another page fed that empty list straight downstream;
- Regression days are the worst: when something breaks we have no call samples that can "replay that exact moment", so we can only reproduce by guessing.

We want a mechanism that can do all of the following:

- While the app runs normally (whether triggered by browser clicks, direct HTTP calls, or via the queue), record **every** backend function call: which function it was, what the api name was, what inputs it received, what outputs it produced, whether it raised, how long it took, and which session it belonged to;
- Store the recording as a file that can be packaged, archived, and put into code review — we routinely `git diff` such files and may also hand them to partners for review, so **reading the same recording back repeatedly must yield the same content**, and even field order must not jump around;
- The recording format is fixed as JSONL (one JSON object per line): **the first line is a file header**, `{"type": "header", "format_version": 1, "gradio_version": <当前 gradio 版本字符串>, "created_at": <创建时间>}`; **each subsequent line is one event** with fields `{"type": "event", "index": <从 0 开始的序号>, "api_name", "fn_name", "session_hash", "inputs", "outputs", "error", "duration", "timestamp"}` — `duration` is the elapsed time in seconds (≥0), `timestamp` is the Unix timestamp of when the event was recorded (>0), and `error` is null when there is no exception. All lines are emitted in the canonical JSON form described above;
- The recording must be **tamper-evident**: if someone sneakily changes a value in some event line (e.g. changes `outputs` from `[3.0]` to `[999.0]`) to make a replay pass, the loader must detect the tampering and refuse to load it — internally we treat this kind of file as a "source of trust";
- After code changes, **without starting a server or opening a browser**, re-run every recorded call against the new app version and automatically compare the new outputs against the recorded ones — identical means pass, changed output means behavioral regression, functions that can't be found at all must be flagged separately, and exceptions are compared by exception **type** (the exact wording of error messages differs every run and does not participate in comparison);
- Calls produced during replay must never be "nested-recorded" by other recorders attached to the same app;
- Recording must not change the behavior of existing apps: **with no recorder attached, everything stays exactly as before**.

## How We Want to Use It

We expect the following names to be exposed directly at the top level of `gradio` for us to use:

- Recorder class `gr.EventRecorder`: bound to a `gr.Blocks`; `start()` / `stop()` control its lifecycle, and both can be called repeatedly at will (idempotent); `start()` returns the recorder itself, so chaining like `gr.EventRecorder(demo, path).start()` works; the current recording state is exposed through the read-only property `is_recording`; the recording file is created only when `start()` is called — merely constructing the recorder must not create the file on disk; it also provides a `close()` — stop recording and fully detach itself from the app (after detaching, not a single hook remains on the app). The `with gr.EventRecorder(demo, path) as rec:` form is also supported: entering starts recording, and exiting stops and detaches with `close()` semantics. Besides blocks and the recording file path, the constructor takes: `include=[...]` (whitelist) and `exclude=[...]` (blacklist), filtering by api name / function name; and `redact=[...]`, which masks sensitive fields (such as "password") from the recording by exact component label match — redacted values are uniformly written as the placeholder `"***"` in the recording, and redaction only affects the recording, not the inputs the function actually receives. Already-recorded events are obtained via `rec.events` (returns a copy). Multiple recorders may be attached to the same app at the same time, each writing its own file. Missing parent directories of the file must be created automatically. Once an event is written it must be flushed to disk immediately — even if the process crashes midway, already-recorded events must not be lost.
- Loader `gr.load_events(path)`: reads back the event list from a recording (excluding the header line itself); raises `FileNotFoundError` if the file does not exist, and raises `ValueError` for any other "this is not a valid recording file" situation (empty file, corrupt header, wrong version, corrupt event lines, tampering).
- Replay function `gr.replay_events(blocks, path, api_names=None)`: re-runs the recorded events one by one against the new app and returns a report; `api_names` can pick only certain functions to replay.
- Report type `gr.ReplayReport` and single-result type `gr.ReplayResult`: the report exposes `total` (total count), `matched` (match count), `mismatched` (behavior-changed count), `missing` (missing-function count), and `errors` (error count) so the numbers are visible at a glance; `results` holds every per-event `ReplayResult` in order, and `mismatches` gives just the "mismatched" entries (the detail list); `ok` is True only if everything matched; `summary()` summarizes the report in one line of text; `to_dict()` converts the whole report into a JSON-serializable dict; and the report works directly as a boolean via `__bool__` (True only if everything matched). Each `ReplayResult` carries `index` (event index), `api_name`, `fn_name`, `status`, `expected`, and `actual`; the status field `status` is a string literal fixed to one of `"match"` (identical), `"mismatch"` (different), `"missing"` (function missing), `"error"` (error).

## Some Key Details — Don't Get Them Wrong

- **The hook must sit at the Blocks call layer** (the `process_api` layer): whether a call comes from an HTTP route, comes out of the queue, or is someone calling `demo.process_api(...)` directly in code, it must be recordable; recording itself **must not** depend on actually starting a server.
- **Which layer counts as "the value the function sees" must be right**:
  - Plain input components (`gr.Number`, `gr.Textbox`, etc.): record the raw payload sent from the frontend;
  - Stateful components like `gr.State`: what the function actually gets is the value in the current session (the frontend payload is ignored by the runtime), so record **the session value the function actually sees**;
  - Plain output components: record the post-processed value;
  - Stateful output components: the payload is usually just a placeholder (`None`), so record **the new session value after the call finishes**.
- **Exceptions**: when the function raises, the event is still recorded with `outputs` as null, and the exception's **class name** (e.g. `"ValueError"`) is recorded in a separate field; the exception itself must propagate **unchanged** — it must not be swallowed.
- **Generators**: only record the first call (the first segment of output); follow-up calls carrying an existing iterator are not recorded.
- **Session isolation during replay**: each event is replayed with a **new session**, and the stateful input values recorded at the time must be injected into this new session before replay (otherwise state-dependent functions like an "accumulator" diverge from the recorded data on the very first call).
- **Serialization**: every recorded value must be JSON-serializable; things that genuinely can't be serialized must be normalized (fall back to strings).
- **Concurrency**: queue + multithreaded concurrent calls must not lose events, and must not produce half lines / interleaved lines / duplicate indices.
- **No recording during replay**: replay goes through the same call pipeline, but recorders attached to the same app must not swallow the calls produced by replay.
- **Consistency judgment in replay**: plain outputs use strict structural equality; exceptions are compared by class name; only "everything matched" counts as `ok` in the report, and a report with zero events has `ok=False`.
- **Compatibility**: the existing APIs, method signatures, and behavior of `gr.Blocks` / `gradio.state_holder.SessionState` must **keep working**, and the repo's existing unit tests must not break because of our changes.

## Some Auxiliary Capabilities to "Get Done Along the Way"

While implementing all of this, you'll notice several capabilities would be much cleaner if sunk into public locations inside Gradio rather than stuffed into a private module. Please make them official user-facing capabilities of Gradio (not "internal contraband"):

- `gr.Blocks` must support "attaching hooks": let third-party code (including our recorder) intervene at the **start** and **end** of every call. The hook signature is fixed as `hook(phase, ctx)`: `phase` is the string `"before"` or `"after"`, and `ctx` is a dict carrying the current call's `api_name` / `fn_name` / `session_hash` / `inputs` / `outputs` / `error` / `duration`; at the `"before"` phase `outputs` is None (the call has not produced anything yet), and at the `"after"` phase `error` is the exception's class-name string when the call raised (None otherwise). The public API is fixed as `add_call_hook(name, hook)` / `remove_call_hook(name)` / `get_call_hooks()` — attach by name, detach by name, and `get_call_hooks()` returns the list of currently attached hook names. **When no hooks are attached, performance must not be dragged down by extra overhead.** Make this a hard contract: a Blocks with not a single hook attached must run `process_api` through an unwrapped fast path — the real implementation body lives on the class's `_process_api_impl` method, calls go straight into it with no wrapping layers stacked in between; in other words, after third-party code replaces `type(blocks)._process_api_impl` wholesale, it must observe that every call enters the replacement implementation.
- `gradio.state_holder.SessionState` must support "taking a snapshot": expose a pair of public methods `snapshot()` / `restore(snapshot)` — `snapshot()` takes a copy of all current stateful component values, and `restore(snapshot)` restores that snapshot exactly as-is. Replay relies on this restore mechanism to "bring back the state of that moment"; this shouldn't be buried in recorder-private code — it's a capability session state should have anyway.
- The **canonical form** Gradio uses internally when serializing JSON (keys in alphabetical order, `ensure_ascii=False`, rejecting `NaN`/`Infinity`, normalizing tuples to lists) should be extracted into a public helper in Gradio, fixed as `gradio.utils.canonical_json_dumps`, so that every place that "needs to write a diffable file" can share it. Recording files should use the canonical form produced by this helper for integrity checks.

## Finally

Put the code in appropriate locations inside the Gradio package, keep code style and type annotations consistent with the repo's existing code, and add adequate pytest unit tests.
