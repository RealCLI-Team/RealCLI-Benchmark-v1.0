# merge-lock design draft (internal, DO NOT SHIP)

Author: p.iyer  |  Date: 2026-07-14  |  Status: draft, superseded by the final spec once approved.

This memo captures the earliest sketch of `pdm merge-lock`, written before the
merge semantics were finalized in the tracking issue. Several of the rules
below were revised after review; treat this file as historical context, not as
the current specification.

## Command surface

```
pdm merge-lock BASE OURS THEIRS [-o OUTPUT] [--on-conflict STRATEGY] [--dry-run] [--json]
```

## Merge rules (draft)

- Package identity = name + extras + source URL + environment marker. Version
  is **not** part of identity.
- Added on one side only → keep. Deleted on one side, untouched on the other →
  delete. Identically changed on both sides → clean.
- Field merges: `groups`, `dependencies`, and the file-hash list take a
  three-way set union; single-value fields (`version`, `requires_python`,
  `summary`, `marker`) take the changed side.
- **`content_hash` follows theirs** — the metadata block is regenerated from
  whichever branch is being merged in, since that side has the freshest
  resolver output. (Note from later review: revisit — the working copy is
  typically the more recent state; this may need to flip to `ours`.)
- Conflict = both sides bumped the same package to different versions,
  removal-vs-modification, same-name adds with different content, same file
  name with different hashes, or diverging marker splits.

## Conflict strategies

- Default `fail`: print each conflict + three-way state to stderr, exit
  non-zero, **write nothing** — the working copy and any `-o` target both stay
  untouched.
- `ours` / `theirs`: take the entire package entry (including deletions) from
  the corresponding side.
- **`newer`: take whichever side has the higher pinned version. On a tie or
  when versions can't be compared, fall back to `ours`.** A modification
  always beats a deletion. (Review comment: the tie fallback should probably
  match `theirs` so that git-driver behavior lines up with what "incoming
  wins" users expect. Confirm before shipping.)

## `[metadata]` merge

- `groups`, `targets`: three-way set rules.
- `lock_version`: max of the two sides.
- `content_hash`: see the draft rule above.
- `strategy` flags (`cross_platform`, `static_urls`, ...):
  - one side changed → take the changed side.
  - both changed in different directions → reject the whole merge (safer to
    force a re-lock than guess).
- Legacy boolean forms (`cross_platform = true` etc.) are dropped from the
  output.

## Automation flags

- `--dry-run`: parse and report, write nothing.
  **Draft: dry-run exits 0 regardless of conflict state so it can be used as a
  cheap check in git hooks.** (Follow-up: the tracking issue wants non-zero on
  conflict here for CI wiring; leave the final call to the spec.)
- `--json`: emit a machine-readable report to stdout. Human-readable messages
  go to stderr so stdout is pipe-friendly.

## Report shape

```json
{
  "clean": true,
  "packages": 4,
  "changes": {
    "added": ["gamma 2.0.0"],
    "removed": ["legacy 0.9.1"],
    "updated": ["alpha 1.5.0"]
  },
  "conflicts": [
    {"package": "alpha", "field": "version", "base": {}, "ours": {}, "theirs": {}}
  ]
}
```

Add / remove / update entries are `"<name> <version>"` strings.

## Output conventions

- Preserve the `@generated by PDM` header.
- All `[metadata]` fields must be present.
- `[[package]]` sorted by name.
- Byte-identical repeat runs on identical inputs.
- Output must round-trip through PDM's own lockfile reader.

## Input validation

- Missing files, TOML parse failures, non-PDM lockfiles (e.g. `pylock.toml`),
  a lock version newer than what this PDM can read: all exit non-zero with a
  clear message.
- Duplicate package entries (identical identity) within one lockfile are a
  corruption error, not a "pick one" case.
