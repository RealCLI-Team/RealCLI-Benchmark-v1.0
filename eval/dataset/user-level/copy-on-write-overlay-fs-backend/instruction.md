We use PyFilesystem2 (the repository at `/app`) to manage a collection of "base datasets". These datasets are shared, read-only baselines for the whole team — nobody is allowed to modify them; but every downstream task wants to make its own changes on top of one — modify a few files, add some new files, delete a few it doesn't need — and it must **absolutely never pollute the baseline**: once the run is over, the baseline must be handed to the next person exactly as it was. The current practice is to make a full copy of the entire baseline before touching it, and copying tens of GB back and forth is slow and wastes disk space.

What I want is a **copy-on-write overlay filesystem** like Linux `overlayfs` / container images: a read-only baseline layer underneath, a writable "change layer" on top, exposed as a single merged, ordinary filesystem. On reads, if the upper layer has the resource, read from the upper layer; otherwise fall through to the lower layer. All writes, modifications, and deletions land only in the upper layer; the lower layer never changes by a single byte.

Please add such a backend in `/app`, with the following requirements:

1. Add a module `fs/overlayfs.py` implementing a filesystem class `OverlayFS`.
   - Construction is `OverlayFS(lower_fs, upper_fs=None)`: `lower_fs` is the read-only lower filesystem, `upper_fs` is the writable upper one; when `upper_fs` is omitted, an in-memory filesystem is used automatically as a "temporary change layer".
   - `lower_fs` is a **read-only baseline**; no operation through the overlay is allowed to modify it.
   - The merged view must have intuitive semantics:
     - **Read-through** — resources missing from the upper layer are transparently read from the lower layer.
     - **Copy-on-write** — when modifying a file that exists only in the lower layer (append, overwrite, metadata changes, etc.), first copy it into the upper layer and then modify it; the change is visible only in the upper layer.
     - **Deletions are expressed with "whiteouts"** — when deleting a resource that exists only in the lower layer, you must not touch the lower layer; instead, record a "this thing has been deleted" marker in the upper layer so it disappears from the merged view; `listdir`, walking, etc. must no longer see it, and of course the internal marker itself must not be exposed.
     - **Directory recreation must be "clean"** — if a non-empty lower-layer directory is deleted and a new directory is created at the same location, the old lower-layer children **must not** reappear; the new directory must behave like a brand-new empty directory.

2. Add an opener so the backend can be opened through the standard entry point `fs.open_fs("overlay://...")`, with protocol name `overlay`. The resource part of the URL specifies the lower filesystem as a nested FS URL (e.g. `overlay://osfs:///data`); `overlay://` without a lower-layer address is equivalent to an empty lower layer plus an in-memory change layer, and it must open and read/write normally. Put the opener under `fs/opener/` and wire it in the way the repository already does.

3. This backend must **work seamlessly** with everything the repository already provides: `fs.copy`, `fs.move`, `walk`, `glob`, the various text/binary modes of `open`, every namespace of `getinfo`, paged directory iteration, cross-backend bulk copies (including the multithreaded workers), and so on — all must behave on `OverlayFS` exactly as they do on the other backends. In particular, when the lower layer is empty, this overlay must be **completely indistinguishable** from an ordinary writable filesystem. In other words, it must be a **fully compliant** PyFilesystem2 backend, not just "mostly working".

As for what "compliant" actually means, the repository itself is the most authoritative specification source: the base class `fs/base.py`, the info model `fs/info.py`, permissions `fs/permissions.py`, open modes `fs/mode.py`, error types `fs/errors.py`, enumerations `fs/enums.py`, path utilities `fs/path.py`, and the existing backends (e.g. `fs/memoryfs.py`, `fs/wrapfs.py`, `fs/multifs.py`) are all reference implementations you can compare against. Use them as the authority to infer the semantics each method should have, its edge cases, and which exception it should raise — including the various error paths (resource not found, type mismatch, destination already exists, directory not empty, improperly writing to the root directory, etc.), which must all align with the repository's existing conventions.

Do not change the original behavior of existing, git-tracked files in the repository; apart from the changes necessary to wire in the opener per point 2, the main work is **adding** code. When finished, this backend should be usable directly as a first-class backend.
