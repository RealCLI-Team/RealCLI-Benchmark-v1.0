We are using PyFilesystem2 (the repo at `/app`) to put a batch of data onto some **not-fully-trusted storage** — shared volumes, object storage, offsite backup drives, and the like. The compliance requirement is: **file contents must be encrypted before they hit the disk**, so that no one rummaging through the underlying storage directly can see plaintext. But we don't want to change the upper-layer business code — it currently just takes a PyFilesystem2 filesystem object and does normal `open`/`read`/`write`/`copy`, and the business side must never have to handle ciphertext by hand.

So I want a "transparent encryption" filesystem backend: it wraps an existing filesystem (call it the "backing store"), looks like an ordinary filesystem from the outside, but **file contents written through it are automatically encrypted, and automatically decrypted when read back** — completely transparent to the business side.

Please add this backend in `/app`. Requirements:

1. Add a module `fs/cryptfs.py` implementing the filesystem class `CryptFS`.
   - Constructed as `CryptFS(backing_fs, key)`: `backing_fs` is the backing filesystem that hosts the data, and `key` is the encryption/decryption key (both str and bytes must be accepted).
   - **Encrypt only file contents**: the directory structure (which directories, which files, how they nest, which entries are files vs. directories) stays in plaintext in the backing store, so that `listdir`, `walk`, `glob`, `move`, `remove`, etc. all keep working as usual.
   - Looking directly at the bytes of the corresponding file in `backing_fs`, **no plaintext content may appear**; reading it back through `CryptFS` must return exactly what was written (covering empty files, binary data, large files, random-seek reads, append writes, and so on).
   - **Sizes must "add up"**: the underlying ciphertext is larger than the plaintext because it carries the extra information needed for encryption/decryption (nonce, checksum, etc.), but what the business sees through `getinfo`/`getsize` must be the **logical size of the plaintext**, with this overhead not counted.
   - **Integrity / wrong keys must be detectable**: if the underlying ciphertext has been tampered with or truncated, or someone reads with the **wrong key**, it must fail loudly (raise an exception), not silently return a pile of garbage.
   - **The same key restores everything**: reopening a `CryptFS` over the same backing store with the same `key` must read back the previously written directories and files exactly as they were.

2. Add an opener so it can be opened through the standard entry point `fs.open_fs("crypt://...")`, with the protocol name `crypt`; both the key and the address of the "backing store" must be passable in the URL (e.g. `crypt://<key>@osfs:///data`). The backing store address may be omitted — the form `crypt://<key>@` without a backing address is equivalent to wrapping an in-memory filesystem, and must open and read/write normally. Put the opener under `fs/opener/` and wire it in the repo's existing way.

3. This backend must work **seamlessly** with everything already in the repo: `fs.copy`, `fs.move`, `walk`, `glob`, the various text/binary modes of `open`, the namespaces of `getinfo`, paginated directory listing, cross-backend bulk copy (including the multithreaded workers), and so on — all of these must behave on `CryptFS` exactly as they do on other backends. In other words, it must be a **fully behavior-compliant** PyFilesystem2 backend, not just "mostly usable".

As for what "compliant" actually means, the repo itself is the most authoritative spec source: the base class `fs/base.py`, the proxy backend `fs/wrapfs.py`, the info model `fs/info.py`, permissions `fs/permissions.py`, open modes `fs/mode.py`, error types `fs/errors.py`, enumerations `fs/enums.py`, and the existing backends (e.g. `fs/memoryfs.py`, `fs/osfs.py`) are all reference implementations to check against. Take them as the authority for inferring the semantics, boundary conditions, and which exception to raise for every method — including the various error paths (resource not found, type mismatch, destination already exists, directory not empty, writing to the root directory improperly, etc.), which must align with the repo's existing conventions. You may design the encryption scheme yourself, using only the Python standard library (no third-party crypto library required); the key is to satisfy the observable properties above: "no visible plaintext, sizes add up, tampering/wrong keys detectable, same key restores".

Do not change the original behavior of existing files already in the repo; apart from the changes necessary to wire in the opener per point 2, the main work is **adding** code. When done, this backend should be directly usable as a first-class backend.
