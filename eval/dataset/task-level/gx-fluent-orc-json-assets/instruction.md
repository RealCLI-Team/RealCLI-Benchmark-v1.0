# Data Governance Review: Broaden great_expectations' "Format Compliance" Coverage and Tighten One Legacy Check

I'm the tech lead of the data platform team; the great_expectations under `/app` is our review tool before data lands in the lake. Last week the governance side delivered a quarterly audit with two pieces of feedback:

## Feedback 1: Add Several New Format-Compliance Checks

The auditors went through the list of existing core Expectations and pointed out that several kinds of fields we run every day have no corresponding official check:

- **Business-system primary keys / event IDs**: we use RFC 4122 UUIDs as business primary keys and event IDs across the board. The auditors require: for such columns we must be able to validate "whether it's a valid UUID", and — because different upstream systems are only allowed to generate specific UUID versions — the check must be able to constrain "only version N accepted". The check is delivered as `ExpectColumnValuesToBeValidUuid` (`expectation_type`: `expect_column_values_to_be_valid_uuid`). "Valid UUID" here means the canonical 8-4-4-4-12 hyphenated form only — brace-wrapped forms, 32-hex-digit forms without hyphens, `urn:uuid:`-prefixed forms, and any value with leading/trailing/internal whitespace all count as invalid (beware: Python's `uuid.UUID()` happily accepts several of these non-canonical forms; this check must not). The version constraint is exposed through a `uuid_version` parameter whose legal set is exactly `{1, 3, 4, 5}`; any other value must raise `ValueError` at construction time.
- **Lake-ingestion timestamps**: timestamps are currently landed as strings (we go through pandas downstream, and not every collection endpoint can guarantee datetime types). The auditors require validating "whether this column is a valid ISO 8601 calendar date or datetime", and genuinely catching invalid calendar dates (nonexistent months, nonexistent days, wrongly judged leap years, out-of-range hours/minutes/seconds) — not just checking whether "it looks like one". They specifically noted that compact forms, US-style forms, pure times, and year-month-without-day must all count as invalid. The check is delivered as `ExpectColumnValuesToBeValidIso8601Datetime`. A space-separated date and time (e.g. `'2026-12-31 23:59:59'`) is a valid datetime form, while an hour of `24:00` and an out-of-range UTC offset such as `+25:00` must be rejected.
- **Payment card numbers (PAN)**: customer-service tickets often have card numbers copied in with spaces or dashes, and we currently have no systematic way to judge whether these card numbers are "structurally valid". The auditors' criterion is industry practice: after removing grouping separators, the digit count is within the standard range (13–19 digits) and it passes the Luhn check. The same digits appearing in integer form must not count as valid input (the semantics we want is "format compliance of a string column"). The check is delivered as `ExpectColumnValuesToBeValidCreditCardNumber`.
- **IBAN accounts**: IBANs in cross-border settlement tables are completely unchecked today. The auditors' exact words: "IBAN has the ISO 13616 registry, every country's length and structure is fixed; you must at least recognize valid IBANs for the dozens of countries in the registry, reject unregistered country codes and ones whose length doesn't match, and pass the mod-97 check." Grouping separators of any whitespace kind (spaces, tabs, newlines) and case differences are common writing habits and must be normalized away before validation, not judged invalid. The country registry to follow is the official SWIFT IBAN registry, which also includes `XK`. The US does not use IBAN; such country codes must be rejected. The check is delivered as `ExpectColumnValuesToBeValidIban`.

We want these four checks to become first-class citizens in core — data engineers should be able to `import` them directly from `great_expectations.expectations` and use them just like calling `ExpectColumnValuesToMatchRegex`; `ExpectationSuite` assembly, YAML/JSON serialization round-trip, the `mostly` threshold, separate null counting, and getting the full violation list with `result_format="COMPLETE"` — these customary behaviors must all match the other core Column Map Expectations in the repo, no more and no less. Running on pandas is the main battleground; if comparable Expectations in the repo also support Spark as a matter of course, stay consistent.

## Feedback 2: `expect_column_values_to_be_json_parseable` Is Too Loose

The same audit also surfaced a real incident: in March we launched a CDC table whose schema declared a column as "JSON records"; it passed review with `ExpectColumnValuesToBeJsonParseable` all green, but downstream deserialization blew up in large numbers — investigation found the real values were heavily mixed with `"null"`, `"123"`, `"true"`, `"\"deleted\""` and the like. From `json.loads`'s perspective these are indeed "parseable", but none of them is a real record.

The auditors' conclusion: **this existing Expectation's notion of "valid" is too loose and must be tightened to "the top level must be a JSON object or array"**. Literal primitives (number / boolean / null / string) should not count as real JSON records in a data-governance context; empty strings, whitespace-only strings, and non-string values certainly don't count either. The original name, parameters, registration, and rendering templates all stay unchanged — only the judgment semantics is tightened, sitting together with the four newly added checks as core's consistent format-compliance family.

## Constraints

- All code is under `/app`; modify the great_expectations source directly.
- Both the newly added checks and the tightened legacy check must be importable and usable as core Expectations through the standard entry points (`great_expectations.expectations` and `great_expectations.expectations.core`); the class-name-to-`expectation_type` mapping follows the repo's existing conventions.
- The customary fields in the validation result object — `element_count`, `unexpected_count`, `unexpected_percent`, `partial_unexpected_list`, `missing_count`, `missing_percent`, and `unexpected_list` with `result_format="COMPLETE"` — must all be present, with field semantics consistent with the repo's existing Column Map Expectations (e.g. nulls go through the missing branch, `mostly` only counts non-null samples).
- For the tightened JSON-record check, don't break its existing prescriptive templates, public import paths, or parameter signatures — data engineers have a pile of Suites referencing it, and breaking even one field name will blow up downstream.
- SQL-engine adaptation is not required for the new checks this time; if comparable Expectations in the repo happen to declare Spark support, stay consistent.
- Please also add integration tests in the same style as the repo's existing Column Map Expectations (the kind that run against a real pandas DataFrame).

## Acceptance

We will run a batch of review Suites against real pandas DataFrames, covering the four new check categories above and the tightened JSON-record check; sample values cover each category's valid/invalid boundaries, common miswritings, `mostly` threshold switching, null behavior, and `ExpectationConfiguration` serialization-deserialization round-trip consistency. It counts as done when the behavior matches the above conventions exactly, and both the new and the tightened existing Expectations register and work properly as core.
