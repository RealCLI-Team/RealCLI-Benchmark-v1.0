We run this networkx source tree in `/app`, and in our downstream graph-data-analysis pipeline we've hit two blockers that we want cleaned up in one go.

**Blocker one — graph isomorphism checks don't scale.**
Our rule graphs and event graphs range from a few hundred to a few thousand nodes, and calling `nx.is_isomorphic(G1, G2)` directly has two problems: first, it is absurdly slow — a few hundred nodes already makes you question your life choices; second, at slightly larger scales it raises `RecursionError` — that VF2 implementation is written recursively and blows the stack. A newer approach in the field is VF2++ (Jüttner & Madarasi, *VF2++—An improved subgraph isomorphism algorithm*, Discrete Applied Mathematics, 2018), which determines the matching order by node-label rarity and degree, uses non-recursive backtracking, and incrementally maintains the candidate frontier (usually denoted T1/T2 and their complements); on the same batch of data it is often one to two orders of magnitude faster than VF2. Please add VF2++ directly into this copy of networkx, making the following usages all work — note that our downstream code uses them after `import networkx as nx` **from the top-level namespace**:

- All three entry points `nx.vf2pp_is_isomorphic(G1, G2)` / `nx.vf2pp_isomorphism(G1, G2)` / `nx.vf2pp_all_isomorphisms(G1, G2)` must exist, covering respectively the three typical needs of "tell me whether they are isomorphic", "if isomorphic, give me a G1→G2 mapping (None if not)", and "enumerate all isomorphism mappings as an iterator, without ever yielding the same one twice".
- Allow a `node_label=` parameter specifying that "only nodes whose value for this node attribute is equal may match each other", together with a `default_label=` giving nodes lacking that attribute a fallback value — this is our standard practice for business labels (node type, color, role, etc.). When the parameters are not given, node attributes are completely ignored.
- All four graph types `Graph`, `DiGraph`, `MultiGraph`, and `MultiDiGraph` must be supported. Directed graphs must genuinely respect edge direction (reversing one edge must make them non-isomorphic); multigraphs must genuinely count how many parallel edges exist between any pair of nodes — one more or one fewer means not isomorphic; directed multigraphs match the multiplicities in the two directions separately.
- Cases that are obviously impossible — different node counts, different degree sequences (in/out degrees separately for directed graphs) — should not actually run the search; give a fast negative answer.
- Only a genuine VF2++ is accepted — wrapping the existing VF2 matcher in a layer that "looks like it", or enumerating in input order with no ordering at all, won't survive at our scale. Non-recursive traversal, the paper's T1/T2 frontier maintenance, and its multi-level pruning must all be written out.

**Blocker two — the existing high-level APIs crash outright on our graph types.**
In our pipeline, graphs are not necessarily undirected, and not necessarily simple — the common combinations are `DiGraph`/`MultiGraph`/`MultiDiGraph`. Using the existing necessary-condition pre-screening functions hits pitfalls:

```python
nx.could_be_isomorphic(some_digraph, some_digraph)       # 抛异常
nx.fast_could_be_isomorphic(some_multigraph, some_multi) # 抛异常
```

Their docs say "returning True does not guarantee isomorphism, returning False guarantees non-isomorphism" — defined that way, on these graph types of ours they **must at least not crash**, and should give reliable necessary-condition judgments (checks on consistency of node count, edge count, degree sequences, and the like must be done where they should be; more expensive properties that can't be computed may be degraded, but they must not lie — they must not declare two obviously different graphs "possibly isomorphic" to the point of losing all screening value). On the undirected simple graphs where they originally worked, please keep their original behavior (the degree/triangle/clique-number set of checks must still be done as before, so our migration introduces no regressions). `nx.faster_could_be_isomorphic` currently runs on all four graph types — please keep it as the fastest, loosest tier. In addition, if one graph is directed and the other undirected, or one is a multigraph and the other simple, then they are **inherently impossible to be isomorphic**, and this tier should give me a direct negative answer instead of blowing up somewhere inside. All three pre-screening functions must also accept the `node_label=` / `default_label=` keyword arguments: when `node_label` is given, treat equality of the label multisets (counting the value each node takes after `default_label` fallback) as an extra necessary condition; when it is not given, node attributes are completely ignored.

**Polish the top-level `nx.is_isomorphic` while you're at it.** We often need to write things like "label-isomorphism matching by some node attribute", and today we can only write a pile of `node_match=lambda a,b: a.get('label') == b.get('label')` ourselves — verbose and slow (still going through VF2). Please give it an optional `node_label`/`default_label` parameter pair, with behavior consistent with the three VF2++ functions above — when `node_label` is given alone, go straight down the fast VF2++ path; when given together with the old `node_match`/`edge_match`, the `node_label` constraint should be layered on top of `node_match`, falling back to the original VF2 matcher (so that `edge_match` logic others have already written is unaffected). Calls that don't pass the new parameters must remain 100% behavior-compatible (including: the old convention that mixing directed/undirected raises `NetworkXError`, and the old results when no match argument is given).
